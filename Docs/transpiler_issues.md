# Py2V Transpiler Issues

The following issues were found during the transpilation of Python code containing class definitions, instance variable initializations, and union types. The output generated by the transpiler fails to compile with the latest V compiler.

### 1. Function names cannot contain uppercase letters (e.g. `new_Data()`)
**Description:**
When a Python class (e.g. `Data`) is transpiled into a V struct, the transpiler generates a factory function `pub fn new_Data() Data`. However, V enforces a strict naming convention where function names must be in `snake_case` and cannot contain uppercase letters.

**Expected Behavior:**
The factory function should be named using snake_case, for example, `new_data()`, or the transpiler should convert uppercase letters to lowercase with underscores appropriately.

**Output from V compiler:**
```
test_transpile.v:6:8: error: function names cannot contain uppercase letters, use snake_case instead
    4 | }
    5 |
    6 | pub fn new_Data() Data {
      |        ~~~~~~~~
```

### 2. Inline sum types are deprecated in V
**Description:**
When a Python instance or class variable is annotated with a union type (e.g. `value: int | str = 0`), the transpiler generates an inline sum type for the struct field: `value int | string`. The V language has deprecated inline sum types and requires named sum types defined via `type MySumType = int | string`.

**Expected Behavior:**
The transpiler should generate a separate `type` definition for union types used in struct fields, and reference that named type in the struct.

**Output from V compiler:**
```
test_transpile2.v:4:11: error: inline sum types have been deprecated and will be removed on January 1, 2023 due to complicating the language and the compiler too much; define named sum types with `type Foo = Bar | Baz` instead
    2 |
    3 | pub struct Data {
    4 |     value int | string
      |           ~~~
```

### 3. Instance variables declared in `__init__` are not collected as struct fields (Without Mypy)
**Description:**
In Python code where instance variables are declared and initialized inside the `__init__` method (e.g. `self.value = 0` or `self.value: int | str = 0`), the transpiler does not collect these as fields for the generated V struct if Mypy type inference is not available or fails. This leads to an empty struct definition `pub struct Data {}`. Subsequent assignments to `self.value` or `d.value` result in V compiler errors because the field is unknown.

**Expected Behavior:**
The transpiler should parse the `__init__` method to detect assignments to `self.*` and automatically add them to the struct definition, even when Mypy metadata is unavailable.

**Output from V compiler:**
```
test_transpile.v:8:10: error: type `Data` has no field named `value`
    6 | pub fn new_data() Data {
    7 |     mut self := Data{}
    8 |     self.value = 0
      |          ~~~~~
```

### 4. Direct assignment of different types to a sum type variable
**Description:**
In the test file, the variable `d.value` is first assigned a string (`d.value = "hello"`) and later an integer (`d.value = 123`). In V, if `value` is a sum type (e.g. `type IntOrString = int | string`), assigning directly requires casting or wrapping in some cases, and calling methods like `.upper()` or adding `+ 1` requires unwrapping the sum type using match statements or type assertions (e.g. `if d.value is string { ... }`). The transpiler currently translates these operations directly (`d.value.upper()`, `d.value + 1`), which will cause compilation errors in V even if the sum type was correctly named.

**Expected Behavior:**
The transpiler should inject type checking/unwrapping logic (like `match` blocks or `as` casts) when operating on variables that are defined as sum types.
